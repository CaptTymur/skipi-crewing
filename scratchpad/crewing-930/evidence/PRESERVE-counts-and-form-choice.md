## Выбор формы: НОВЫЙ ВАРИАНТ `CommittedActive`, не переформовка

проглатывают добавление ПОЛЯ молча. То есть переформовка принуждает там, где компилятор
видит форму, и прячет там, где стоит `{ .. }`.

## Грабля прибора, которую стоит помнить

Catch-all искал шаблоном `_ =>` — по joint-файлу он дал НОЛЬ. Ложный ноль: настоящее плечо
написано `other=>`, именованным джокером. Поймал чтением строк, а не счётчиком.
Класс тот же, что и у составного `#[cfg(all(test, …))]`: шаблон отвечает на вопрос об
ОДНОМ НАПИСАНИИ, а вопрос был о СВОЙСТВЕ.

## ОТВЕТ НА «ЧТО ВОЗВРАЩАЕТ `commit_core` ДЛЯ АКТИВНОГО СЛУЧАЯ» — измерено, не осталось вопросом

**`CommitOutcome` (`native_lifecycle.rs:183-187`) — три варианта: `Ready`, `CommittedPublicationFailed`,
`CommittedBlocked`. `Ready` — UNIT-вариант: об авторизации он не несёт НИЧЕГО.**

У производителя (`native_lifecycle.rs:462-475`) решение об авторизации в этот момент УЖЕ ПРИНЯТО:

```rust
let ready = blocked.is_none();
self.denied.store(!policy.authorizes(ready), Ordering::SeqCst);   // :463
...
return if let Some(reason) = blocked { CommitOutcome::CommittedBlocked {…} }
       else { CommitOutcome::Ready };                              // :474 — решение НЕ попадает в возврат
```

То есть результат `policy.authorizes(...)` уезжает БОКОВЫМ КАНАЛОМ — в `self.denied` и в
`proposed.native_authorized` (`:396`), — а возвращаемое значение различает только
«заблокировано / не заблокировано».

**И отсюда прямое доказательство, что решение теряется на проекции: ОДИН И ТОТ ЖЕ
`CommitOutcome::Ready` проецируется в ДВА ПРОТИВОПОЛОЖНЫХ смысла:**

- `native_local_commit.rs:277` — `CommitOutcome::Ready => LocalOutcome::CommittedInactive{…}`
- `native_local_joint_tests.rs:277` — `CommitOutcome::Ready => JointOutcome::AuthorizedFoundation`

Оба верны СЕГОДНЯ только потому, что каждое место знает, какую политику передал его вызывающий.
Эта связка типам невидима: политика — аргумент, исход её не несёт. **Вот она, единственная точка,
где можно ошибиться молча**, и именно поэтому «поменять литерал политики» дало бы либо всегда
активную сессию, либо всегда неактивную — по тому, какую ветку проекции угадали.

### Следствие для формы фикса (в заявку на фикс)

Недостаточно добавить `LocalOutcome::CommittedActive` и отобразить `Ready → CommittedActive`:
`Ready` не говорит, авторизовано ли. Варианты:

1. **`CommitOutcome::Ready { authorized: bool }` (или отдельный вариант) — ГРОМКИЙ.**
   `CommitOutcome::Ready` встречается текстуально 14 раз (12 в `native_lifecycle.rs`, 1 в
   `native_local_commit.rs`, 1 в joint-тестах); unit-образец не матчит struct-вариант, значит
   компилятор заставит разобраться на КАЖДОМ из них. Две противоположные проекции становятся
   выводимыми из ДАННЫХ, а не из знания вызывающего.
2. **Проекция читает `native_authorized`/`self.denied` — ТИХИЙ.** Типы не меняются, поэтому
   ничто не заставит согласовать вторую проекцию, и два места продолжат расходиться.

Рекомендация: (1). И тогда требование менеджера «точка построения покрыта утверждением, а не
только компилятором» выражается так: тест на ОБЕ стороны развилки, утверждающий, что
спроецированный вариант СОГЛАСЕН с тем, что ядро сообщило, и с наблюдаемым `native_authorized`.
Такое утверждение ловит потерю авторизации на проекции даже при появлении третьего варианта политики.
